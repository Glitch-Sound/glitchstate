# 設計

## 背景と制約

- 提案: [proposal.md](proposal.md)
- 前提: `openspec/tech.md`のアーキテクチャ、技術上の判断基準、テスト方針と、`openspec/structure.md`の配置原則、依存方向に従う。
- 現状: `src/extension/extension.ts`はコマンド実行ごとに起動確認用のWebviewを作り、`src/webview/app/main.tsx`は固定の文言を表示する。
- 現状: Core、DSLサンプル、単体テストはなく、拡張統合テストはコマンド登録だけを確認している。
- UIの制約: 利用者が指定した承認済みUIに合わせ、状態定義表の列見出しは左から色、状態、意味とし、色列は色見本のみを表示する。
- 参考: [GlitchFlowのREADME](https://github.com/Glitch-Sound/glitchflow/blob/main/README.md)と、同じマシンの`/Users/glitch/Developer/glitchflow`のコミット`c2da15951724d608f7d9d800c4bf5afb5e9c5157`を確認した。\
  宣言の`ID as "表示名"`、4個の空白を使う本文、Coreの表示用モデル、文書の版の確認、Webviewの準備完了通知を参考にする。\
  ローカルの実装の参照先は`src/core/parser/parse-glf.ts`、`src/core/model/glf-model.ts`、`src/extension/extension.ts`、`src/extension/preview-panel.ts`である。

## 設計判断

### D-01 - 宣言とインデントによる状態の記法

- 選択: 次の形式を採用し、IDと表示名を分ける。\
  意味は必須のインデント付き本文とし、複数行を受け付ける。\
  数値の順序項目を設けず、宣言の並びを順序とする。
- 理由: GlitchFlowの宣言と本文の書き方を踏襲でき、将来の参照に使うIDを表示名の変更から独立させられる。
- 代替案: JSON、波括弧によるブロック、数値のorder項目は、参考DSLとの記法の差や順序の二重管理が生じるため採用しない。
- 昇格: なし。

```gls
State IDLE as "待機" color "#4F46E5":
    開始を待つ状態
    開始要求を受けたら処理へ進む

State RUNNING as "実行中" color "#22C55E":
    処理を実行している状態
```

記法と入力制約の正本は差分仕様のREQ-001とREQ-002とする。\
コメント、import、タイトル、数値の順序、意味の行内記法は追加しない。\
意味の文字列を評価せず、色を表す値は許可した16進形式だけを受け付ける。

### D-02 - Coreの共通モデルと通信契約の分離

- 選択: `src/core/model/gls-model.ts`に文書の表示用モデルと診断の型を置き、`src/core/index.ts`を公開入口とする。\
  共通モデルの`states`配列は、`id`、`name`、`meaning`、`color`を定義順に保持し、描画ライブラリやVS Codeの型を含めない。\
  配列の位置を表示順とし、独立した順序値は持たない。\
  解析結果は成功時のモデルまたは失敗時の診断を区別し、失敗時に不完全なモデルを描画側へ渡さない。
- 選択: 新設する`src/preview-protocol/`に通信契約を置き、Coreの共通モデルを参照する。\
  ExtensionとWebviewはこの契約を参照し、通信契約から両者の実装を参照しない。\
  Coreは通信契約に依存しない。
- 理由: モデルを状態定義表以外にも利用でき、文書URIや版などの転送用情報をCoreの状態定義から分離できる。
- 代替案: CoreにWebview用の全メッセージを置く案と、両側にメッセージ型を複写する案は、それぞれ責務の混在と変更漏れを招くため採用しない。
- 昇格: openspec/structure.md の ディレクトリ構成。

| データ | 内容 | 責務 |
| --- | --- | --- |
| 表示用モデル | 定義順の状態ID、状態名、意味、カラー | Core |
| 解析診断 | 理由を識別するコード、日本語の説明、1始まりの元の行番号 | Core |
| プレビュー通知 | 通知種別、対象URI、文書の版、通知の通し番号、表示モデルまたは表示不能、現在のエラー有無 | 通信契約 |
| 準備完了通知 | Webviewが受信と描画を開始できること | 通信契約 |
| 描画完了通知 | 対象URI、文書の版、通知の通し番号 | 通信契約 |

診断からVS Codeの0始まりの行範囲への変換はExtensionで行う。\
通信の受信値は外部境界のデータとして検証し、想定外の通知では状態を変更しない。\
描画完了通知は、実際に描画した通知を識別するために使い、DSL本文や任意のコマンドを受け付ける用途には使わない。

### D-03 - 行を保った構文解析と定義検証

- 選択: `src/core/parser/`で宣言と本文の構文解析を行い、`src/core/validator/`で名前、ID、カラー、必須本文、重複IDを検証する。\
  元の行番号を保持したまま改行形式を正規化し、空白だけの行を除き、意味の行から先頭4個の空白だけを取り除く。\
  誤ったインデントや未対応の記述を黙って読み飛ばさない。\
  新しい依存は追加しない。
- 理由: 今回の文法は宣言と平坦な本文だけであり、既存のTypeScriptで解析と検証を分離できる。
- 代替案: YAMLや汎用パーサーの導入は依存と対応文法が必要以上に広がるため採用しない。
- 昇格: なし。

エラーがあっても原因と行は返すが、一部だけ成功した状態配列を正常な表示モデルにはしない。\
本文の不足は宣言行、重複は2件目の宣言行、不正な本文のインデントはその本文行を指す。\
重複判定のキーはIDの原文とし、表示名の重複は許可する。

### D-04 - 文書の版と準備完了通知による更新

- 選択: `package.json`で拡張子`.gls`と言語ID`glitchstate`を登録する。\
  `glitchstate.openPreview`でアクティブな対象文書を単一のパネルへ結び付け、同じパネルを再利用する。\
  別のエディタへのフォーカス移動だけでは対象を変えない。
- 選択: Extensionは`TextDocument.getText()`を使い、開く操作と`onDidChangeTextDocument`から同じ解析入口を呼ぶ。\
  通知対象のURIと版を確定し、対象の切り替えや新しい編集の後に古い結果を採用しない。\
  Webviewには通し番号を含め、同じ表示先で古い通知を描画しない。
- 選択: Webviewの準備完了までは最新の通知だけを保持し、準備完了時や再表示時に最新の状態を送る。\
  パネル破棄時はメッセージ購読とパネル固有の状態を破棄し、拡張機能の破棄時は文書の監視と診断も解放する。\
  閉じた文書のキャッシュは削除し、後から同じURIを開く場合もその文書の現在の内容を解析する。
- 理由: 保存済みのファイル読み込みや送信だけの更新では、未保存の内容や起動時の通知を取りこぼすためである。
- 代替案: 保存イベントだけの監視、ファイル監視、一定間隔のポーリングは採用しない。
- 昇格: なし。

今回の短い同期解析ではデバウンスを導入せず、調整する更新間隔の値は設けない。\
古い結果のテストは、外部境界の通知順を制御して逆転させ、時間待ちの長短で判定しない。

```mermaid
flowchart LR
    A["編集中の.gls"] --> B["Extensionが本文と版を取得"]
    B --> C["Coreが解析と検証"]
    C --> D["共通モデルまたは診断"]
    D --> E["Extensionが最新の版か確認"]
    E --> F["準備完了後に最新の通知を送信"]
    F --> G["Webviewが状態定義表を更新"]
    G --> H["描画完了を通知"]
```

### D-05 - 表の描画とテーマへの追従

- 選択: `src/webview/pages/preview/`にプレビュー画面を置き、appは起動と通信接続を担当する。\
  左から色、状態、意味の3列を持つHTMLテーブルを共通モデルだけから描画し、状態列には状態名を表示する。\
  色列はSVGの図形による色見本のみとし、`fill`属性に共通モデルの検証済みのカラー値を渡す。\
  色セルにカラー値などの表示用テキストを置かず、状態IDは共通モデルに保持する。\
  意味はテキストとして描画し、CSSの`white-space: pre-wrap`で改行を保持する。
- 選択: 表の基本色はVS Codeのテーマ変数を参照し、横罫線を基本にする。\
  状態0件の案内と、正常なモデルがない場合の解析エラーの案内を分ける。\
  初期の見出しと案内文言は画面側の1か所にまとめる。
- 理由: 承認済みUIの列順と色見本のみの表示に合わせ、DSLの再解析や生のHTML挿入を表示側に持ち込まず、指定カラーとテーマの役割を分けられる。\
  動的な色のために既存のCSPでインラインスクリプトを許可する必要もない。
- 代替案: 状態ごとに固定の色クラスを列挙する案は任意の指定カラーを扱えず、意味をHTMLとして挿入する案は文字列の解釈が変わるため採用しない。
- 昇格: なし。

新しい寸法や固定の背景色はこの変更の約束にせず、既存の余白を出発点とする。\
テーマ変数以外の調整値を追加する必要が生じた場合は、実装より先にこの判断へ値、理由、1か所の定義先を追記する。

### D-06 - 正常なモデルと現在の診断の分離

- 選択: ExtensionはURIごとに最後の正常なモデルを保持する。\
  現在の解析に失敗したときは診断だけを更新し、同じURIの正常なモデルがあればそれを通知する。\
  そのURIの正常なモデルがなければ表示不能を通知する。\
  空の文書のモデルは成功として記録し、以前の状態行を消す。
- 理由: 入力途中の表の消失を避けつつ、別文書の正常な表や過去の診断の混入を防げる。
- 代替案: 最後の表をURIに関係なく1つだけ保持する案と、エラー時に常に全表示を消す案は採用しない。
- 昇格: なし。

### D-07 - テスト境界とプロダクト検査

- 選択: CoreはVitestで返却値全体と診断の行と理由を確認する。\
  Extensionの単体テストではVS Codeの文書、変更通知、Webview送受信を境界として差し替える。\
  既存のVitestの収集設定にExtensionの単体テストを追加する。
- 選択: Playwrightで実際のプレビュー画面に通知を渡し、列見出しが色、状態、意味の順であること、行数、各セル、行の並び、色見本の属性、色セルに表示用テキストがないこと、改行、空表示、実行されない文字列、準備完了時の受信を検証する。\
  acquireVsCodeApiの代替はテスト用の起動処理に閉じ込め、製品にブラウザー専用の起動分岐を追加しない。
- 選択: VS Code統合テストで実際の`.gls`文書、未保存の編集、コマンド、Problems、対象切り替えを確認する。\
  必要な描画待ちは対象URI、版、通知番号を照合した描画完了通知で行い、単に送信できたことを描画成功としない。\
  `tests/extension/suite.cjs`は既存の確認を保ち、新しいテストモジュールを呼ぶ入口とする。
- 選択: `package.json`の`check:product`に追加した単体、ブラウザー、VS Code統合の検査を含め、`check`から引き続き呼ぶ。\
  Playwrightの起動先設定と必要なテストランナーの収集設定を更新する。\
  VS Codeテスト用バイナリとPlaywrightのブラウザーが必要なことをセットアップ手順へ追記する。
- 理由: 模擬通信だけでは実際の未保存文書の取得や診断登録を検出できず、VS Codeのホスト内だけでは表のDOMの誤りを十分に切り分けられないためである。
- 代替案: 全経路を手動だけで確認する案と、DOMのHTML全文のスナップショットだけで判定する案は採用しない。
- 昇格: なし。

## リスクと移行

- DSLの記法は初回の導入であり、既存の`.gls`データの移行はない。\
  参考にしたGlitchFlowの全記法への互換性は提供せず、対応する状態定義の記法をREADMEとサンプルに明記する。
- 準備完了前の送信、URIの切り替え、古い版の通知は、誤った表を残す原因になる。\
  通知番号とURIと版の照合、準備完了時の再送、境界を逆転させるテストで対処する。
- エラー中の表は現在の本文と一致しない場合がある。\
  現在の診断と最後の正常なモデルを分け、正常なモデルの有無を通知に含める。
- `check:product`にブラウザーとVS Code統合の検査を追加すると、実行環境の準備が必要になる。\
  依存する実行環境をREADMEへ記載し、検査の無効化や成功扱いへの置き換えでは対処しない。
- 変更を戻す場合は、この変更で追加した言語登録、Core、通信契約、プレビュー、テスト、文書をまとめて戻す。\
  利用者の`.gls`ファイルを書き換える処理は追加しない。
