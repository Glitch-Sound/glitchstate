# 技術方針

技術の選定、判断の基準、テストの方針を定める。\
コードの置き場所は structure.md、要件は specs に書き、ここには書かない。

## 技術スタック

使う言語、ライブラリとその版は、`package.json` と、言語ごとの依存の定義ファイルを正とする。\
ここには、主要なものだけを書く。

- 言語: TypeScript(strict)
- 開発環境: Visual Studio Code
- 拡張機能: VS Code Extension API
- UI: React 19
- 状態遷移図: React Flow(@xyflow/react)
- スタイル: Tailwind CSS 4 + CSS + VS Code Theme Variables
- UIプリミティブ: Radix UI(必要なコンポーネントのみ)
- アイコン: Lucide Icons(lucide-react)
- クライアント状態管理: Zustand
- スキーマ検証: Zod 4
- Webview: VS Code Webview API
- Webviewビルド: Vite
- Extensionビルド: esbuild
- アーキテクチャ: Feature-Sliced Design v2.1(Webview)
- 静的解析・フォーマット: Biome
- FSDルール検査: Steiger
- 型検査: TypeScript Compiler
- 単体テスト: Vitest
- UI・視覚テスト: Playwright
- VS Code統合テスト: @vscode/test-electron
- 依存管理: pnpm
- 仕様管理: OpenSpec

### 採用しない技術

- shadcn/ui: 独自UI中心のため初期採用しない
- TanStack Query: サーバー状態を管理しないため不要
- React Router: 単一プレビュー画面のため不要
- React Hook Form: DSL主体で入力フォームを持たないため不要
- TanStack Table: 独自の状態遷移マトリクスを実装するため不要
- Turborepo: 単一パッケージ構成のため不要

必要になった段階で再評価する。
各ライブラリのバージョンはpackage.jsonとpnpm-lock.yamlを正とする。

## アーキテクチャ

### 基本構成

Core、Extension、Webviewを分離する。\
CoreはVS Code APIやDOMに依存しない純粋なTypeScriptで構成する。\
ExtensionはVS Codeとの連携を担当し、Webviewは表示とユーザー操作を担当する。\
WebviewにはFSD v2.1を採用し、Pages Firstで必要な構造から実装する。

### Core

- DSLの構文解析
- 状態・イベント・遷移のモデル化
- 構文および意味の検証
- 参照整合性の検証
- 表示用中間モデルの生成

状態定義・状態遷移図・状態遷移表は、同一の中間モデルから生成する。

### Extension

- `.gls`ファイルの言語登録
- DSLの変更監視
- Coreによる解析結果の管理
- Webviewの生成とメッセージ通信
- 診断結果のVS Codeへの通知
- エディタとプレビューの連携
- 画像エクスポートの保存処理

保存前の編集内容もプレビューに反映する。\
編集による再解析では、古い結果が新しい結果を上書きしないようにする。

### Webview

Reactで状態定義・状態遷移図・状態遷移表を描画する。\
状態遷移図にはReact Flowを使用する。

- 状態定義: HTMLテーブル
- 状態遷移図: React Flow
- 状態遷移表: HTML/CSSによるマトリクス
- 状態の選択情報: 各表示領域で共有
- 表示内容: Coreの中間モデルから生成

表示領域ごとにDSLを再解析しない。

### データフロー

1. ExtensionがDSLの変更を検知する。
2. Coreが構文解析と検証を行う。
3. Coreが共通の中間モデルを生成する。
4. ExtensionがWebviewへモデルを通知する。
5. Webviewが3つの表示領域を更新する。

### 外部サービス

外部サービスへの依存は設けない。\
DSLの解析と描画はローカルで完結させる。

## 技術上の判断基準

- 既存の依存や仕組みで足りる場合は、新しい依存を追加しない。
- 新しい依存を追加する場合は、理由を change の設計に書く。
- 外部サービスや外部ライブラリとの接続は、境界の1か所にまとめる。
- 関数とモジュールは、1つの責務に絞る。\
  検証、変換、入出力、後始末など、性質の違う段階を1つの関数にまとめない。
- 外部との境界(ファイル、外部ライブラリ、時刻、乱数、外部サービス)は、引数で受け取れるようにし、テストで代わりのものを渡せるようにする。\
  境界でない内部の処理どうしには、差し替えのための仕組みを作らない。
- 設定値や秘密情報は、コードに直接書かず、設定ファイルや環境変数から読む。
- DSLを設計情報の唯一の定義元とする。
- 状態定義・状態遷移図・状態遷移表で個別の設計情報を保持しない。
- 同一の解析結果から各表示領域を生成し、表現間の整合性を保証する。
- 状態の表示順序はDSLの状態定義順を基準とする。
- イベントカテゴリはDSLで定義し、表示側で固定しない。
- 複数状態のグループ化はDSLで明示された場合のみ適用する。
- グループ化は図の表現であり、個々の状態遷移の意味を変更しない。
- 条件分岐は共通処理と分岐ごとの処理・遷移先を区別できるモデルとする。
- React Flowへの依存は図の描画領域に閉じ込める。
- React Flow固有のNode/Edge型をCoreのドメインモデルに持ち込まない。
- UIはGlitchBoard・GlitchFlowと一貫した操作性を維持する。
- VS Codeのテーマと調和するフラットな配色とし、不要なグラデーションや装飾を避ける。
- 状態の強調は控えめな背景色を基本とし、不要な枠線を使用しない。
- 表は横罫線を基本とし、条件分岐など意味のある箇所に限り縦線を使用する。
- 図上ではイベントを表示せず、イベントとの対応は状態遷移表で確認できるようにする。
- 画像エクスポートと拡大縮小の操作はGlitchFlowに合わせる。
- DSLの内容を実行可能コードとして評価しない。
- 解析エラーがある場合は診断を表示し、可能な限り最後の正常な描画を保持する。

プロジェクトで決めた原則は、ここに追記する。

## コードのコメント

- 外から使うモジュール、クラス、関数には、言語のドキュメントコメントで概要を書く。\
  1行目に、モジュールはその役割を、クラスと関数は何をするかを要約する。\
  外から使うものの範囲は、言語の慣習に従って決め、この節に追記する。
- 外から使う関数とメソッドには、引数、戻り値、送出する例外やエラーを、言語の標準の書式で書く。\
  型ではなく、意味、単位、範囲、値がない場合の意味を書く。\
  引数や戻り値がない場合は、その項目を省く。
- ファイルの書換えなどの副作用がある場合は、要約の後の本文に書く。
- 外から使わない関数には、名前と型から目的が分からない場合だけ書く。
- 処理の中のコメントには、なぜそうするかだけを書き、何をしているかは書かない。
- コメントは日本語の常体で書き、2文以上になる場合は1文ごとに改行する。\
  標準の書式の見出しや記号は、言語の書式のままにする。
- プロダクトのコードのコメントには、要件やシナリオの ID を書かない。\
  ID とコードの対応は、テスト方針に従ってテストで管理する。
- ドキュメントコメントの有無と、引数、戻り値、例外の記述が実際の定義と合っているかを、言語の静的解析で検査し、プロダクトの検査に含める。\
  テストのコードは対象から外す。\
  文末の記号を検査する規則は、日本語の句点に合わない場合は使わない。\
  使う道具と規則は、この節に追記する。

TypeScript Compiler APIを使う `scripts/check-doc-comments.mjs` で、プロダクトのTypeScriptファイルのモジュールコメント、公開関数とクラスの概要、公開関数と公開メソッドの引数と戻り値の記述を検査する。\
関数本体の直下で送出する例外には、`@throws` の記述を求める。

## テスト方針

- 単体テストを基本とし、外部との境界は結合テストで確かめる。
- テストの置き場所は、structure.md に従う。
- シナリオIDは、テスト関数のドキュメントコメントの先頭行か、テスト名の先頭に書く。
- 画面の見た目など、自動で判定しにくいものは、manual-checks.md の実機確認で扱う。
