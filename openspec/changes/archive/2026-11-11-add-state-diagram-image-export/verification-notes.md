# 実装と検証の記録

## 保存する内容

保存操作はGlitchFlowと同じ`⇩`からPNGとSVGの形式選択、保存先選択へ進む。\
現在表示できる図全体を対象とし、状態の選択強調を除外して、通常の背景と現在のテーマの不透明背景を保存する。\
Webviewは現在のDOMの配置、名前の行と矢印から単独SVGを生成し、そのSVGからPNGを作る。\
Extensionは要求と現在の通知を照合して、保存先へ画像のバイト列を書き込む。

## 再送の修正とPNG検査の補強

REQ-043-S07では、実際のPNG用画像の読み込み後に変換を待機させ、同じURI、version、sequenceと表示内容を別の通知オブジェクトとして再送した。\
修正前は成功応答を期待するassertで失敗し、実際の応答は失敗だった。\
Webviewが同一通知で取得先と描画世代を無効化しないよう修正した後は、元の要求の成功応答1件と、実際にデコードできるPNGを確認した。\
同一文書の内容更新と別文書への切替をPNG生成中に挟む2件は修正前から成功し、修正後も古い画像を返さず、再操作で異なる名前と遷移先の図を保存できた。

Extensionの接続確認では、表示状態の通知による同一内容の再送後もPNG生成要求が1件で、指定先への書き込みは独立したPNGデータのバイト列で1回だけだった。\
この確認と、PNGの生成待機中の内容更新と文書切替による書き込み0回、再操作の2件は最初から成功した。\
Extensionは既にURI、version、sequenceで要求を照合しており、変更は不要だった。\
保存フローとプレビューの接続の単体91件、古い通知の拒否と小さい版番号での再オープンの既存ブラウザー6件も成功した。
